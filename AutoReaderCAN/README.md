# AutoReaderCAN

Пассивный монитор CAN-шины автомобиля Geely на базе ESP32-C3
(WEMOS LOLIN C3 Mini) и ESPHome.

Устройство **только слушает** шину (режим `LISTENONLY`), ничего не передаёт и
не мешает работе автомобиля. В лог выводятся **все кадры шины** (по каждому ID
с ограничением частоты), периодическая **таблица всех ID** (видно, какие блоки
шлют данные и с каким периодом), а диагностический обмен дополнительно
расшифровывается как **UDS (ISO 14229)**.

На OLED-экран выводятся: количество ID на шине, кадров/сек, расшифрованных
пакетов, ошибок ISO-TP и отрицательных ответов (NRC).

| Файл | Назначение |
|---|---|
| `autoreadercan.yaml` | конфигурация ESPHome |
| `uds_decode.h` | декодер ISO-TP + UDS (подключается через `esphome: includes`) |

## Подключение

### Дисплей 0.42" 72x40 (I2C, SSD1306)

| Дисплей | ESP32-C3 |
|---|---|
| VCC | 3V3 |
| GND | GND |
| SDA | GPIO5 |
| SCL | GPIO6 |

Модуль — 72×40 (SSD1306/SSD1315), адрес обычно `0x3C`. В отличие от 128×64
панелей, у 72×40 контроллер работает с колонками со смещением 28 — ESPHome
делает это сам для модели `SSD1306 72x40`.
Если экран остаётся чёрным, попробуйте `address: 0x3D`.
На плате C3 Mini есть отдельные пины с надписью `SDA`/`SCL` — это **GPIO8/GPIO10**;
если дисплей подключён к ним, измените пины в блоке `i2c`.

### Кнопка и таймаут экрана

Экран гаснет через 30 секунд после включения или последнего нажатия
(настройка `screen_timeout_ms` в `substitutions`). Разбудить — кнопкой на
**GPIO9** (на плате LOLIN C3 Mini это кнопка BOOT; внешняя кнопка — между
GPIO9 и GND, внутренняя подтяжка уже включена).

- Нажатие в выключенном состоянии включает экран и запускает новый отсчёт.
- Нажатие при включённом экране просто продлевает его работу на 30 с.
- Любое нажатие также коротко мигает синим светодиодом.
- GPIO9 — strapping-пин: если держать кнопку при включении/сбросе, ESP32
  уйдёт в режим загрузчика вместо приложения. Обычное нажатие во время работы
  этому не мешает.

### Синий светодиод на GPIO8

Светодиод коротко (по умолчанию 40 мс) вспыхивает на каждый успешно
расшифрованный UDS-пакет и на каждое нажатие кнопки. Ошибки ISO-TP и «мусор»
со шины не подсвечиваются.

```yaml
substitutions:
  # true  - светодиод между +3.3В и GPIO8 (горит при низком уровне)
  # false - светодиод между GPIO8 и GND (горит при высоком уровне)
  led_inverted: "true"
  led_blink_ms: "40"

output:
  - platform: gpio
    id: led_blue
    pin:
      number: GPIO8
      inverted: ${led_inverted}

script:
  - id: led_blink
    mode: single
    then:
      - output.turn_on: led_blue
      - delay: ${led_blink_ms}ms
      - output.turn_off: led_blue
```

Вспышка запускается из колбэка декодера
(`uds_decode::reader().set_on_message(...)`), поэтому реагирует именно на
собранное и распознанное сообщение, а не на любой кадр.

`mode: single` не даёт вспышкам «слипаться»: при плотном потоке пакетов
светодиод мигает не чаще одного раза в 40 мс.

GPIO8 — тоже strapping-пин. При `led_inverted: true` он подтянут к +3.3В через
светодиод, что для загрузки безопасно. Если светодиод подключён к GND и мешает
загрузке, отключите его на время прошивки.

### CAN-трансивер

Нужен трансивер на **3.3 В** (SN65HVD230, TJA1051T/3, MCP2542 и подобные).

| Трансивер | ESP32-C3 |
|---|---|
| VCC | 3V3 |
| GND | GND |
| CTX / TXD | GPIO0 |
| CRX / RXD | GPIO1 |

- Модули на TJA1050 рассчитаны на 5 В, их выход RXD нельзя подключать к ESP32
  напрямую без согласования уровней.
- Шина CAN — дифференциальная: `CAN-H` и `CAN-L` подключаются к разъёму OBD-II
  (обычно контакты **6** и **14**), питание брать с контактов 4/5 (GND) и 16 (+12 В
  через DC-DC).
- Если устройство стоит в середине шины/на коротком шлейфе, может понадобиться
  терминатор 120 Ом между CAN-H и CAN-L.

## Сборка и прошивка

```bash
esphome run autoreadercan.yaml
```

Логи смотреть по USB:

```bash
esphome logs autoreadercan.yaml
```

Если логов не видно (на некоторых клонах C3 Mini стоит отдельный USB-UART
CH340), замените в блоке `logger` строку
`hardware_uart: USB_SERIAL_JTAG` на `hardware_uart: UART0`.

Для работы достаточно USB-питания — Wi-Fi/API по умолчанию отключены
(блоки `wifi`/`api`/`ota` в конце конфига можно раскомментировать).

## Что видно в логе

### Все блоки на шине

При старте каждый новый ID помечается в логе, дальше по каждому ID печатается
последний кадр (не чаще одного раза в `log_throttle_ms`):

```
[I][can_monitor] новый ID STD 0x0A0 (DLC 8)
[I][can_monitor] новый ID STD 0x1A0 (DLC 8)
[I][can_monitor] новый ID EXT 0x18DAF110 (DLC 8)
[D][can_monitor] STD 0x0A0 [8] 00 1A 2B 3C 4D 5E 6F 70
[D][can_monitor] EXT 0x18DAF110 [8] 03 62 F1 90 4C 53 56 00
```

Раз в `table_dump_ms` (по умолчанию 10 с) печатается сводная таблица: ID,
количество кадров, средний период и последние данные. По ней сразу видно, какие
блоки вообще присутствуют на шине и кто из них «живой»:

```
[I][can_monitor] --- шина: ID=3, FPS=512, всего кадров=128734 ---
[I][can_monitor] STD 0x0A0 cnt=   5120 T=  100ms [8] 00 1A 2B 3C 4D 5E 6F 70
[I][can_monitor] STD 0x1A0 cnt=   1280 T=  500ms [8] 12 34 56 78 9A BC DE F0
[I][can_monitor] EXT 0x18DAF110 cnt=     12 T= 1000ms [8] 03 62 F1 90 4C 53 56 00
```

ID, который молчит дольше 30 секунд, из таблицы и со счётчика `IDs` пропадает.

### Расшифрованный UDS

```
[I][uds] [0x7E0] REQ ReadDataByIdentifier VIN(0xF190)
[I][uds] [0x7E8] RSP ReadDataByIdentifier VIN(0xF190)="LSVAA2BM1LN1234567"
[I][uds] [0x7E8] RSP DiagnosticSessionControl extended(0x03) P2=50ms
[I][uds] [0x7E0] REQ ReadDTCInformation sub=0x02
[I][uds] [0x7E8] RSP ReadDTCInformation sub=0x02 DTC=2: P0301-2F[24] U0100-00[24]
[I][uds] [0x7E8] NRC 0x31 requestOutOfRange (сервис 0x22)
```

Расшифровываются:

- сервисы UDS (`0x10`, `0x11`, `0x14`, `0x19`, `0x22`, `0x27`, `0x28`, `0x2E`,
  `0x31`, `0x3E`, `0x85` и другие — с именами и параметрами);
- многосегментные (ISO-TP) сообщения: First Frame → Consecutive Frame → сборка;
- DID с именами (`0xF190` VIN, `0xF187` номер детали, `0xF188`/`0xF189` версии ПО,
  `0xF18C` серийный номер и т.д.), строковые значения печатаются как текст;
- коды неисправностей DTC в формате `P0301-2F` (код + Failure Type + статус);
- Negative Response Code с текстовым пояснением (`conditionsNotCorrect`,
  `securityAccessDenied`, `requestOutOfRange`, ...).
- заодно распознаются OBD-II сервисы (`01`…`0A`), которые ходят по тем же ID,
  в том числе VIN по Mode 09 PID 02:
  `[0x7E8] RSP OBD requestVehicleInfo VIN="LSVAA2BM1LN123456"`.

## Счётчики на экране

На 72×40 помещается 4 строки по ~14 символов:

```
Pkts 1234      <- расшифровано UDS-сообщений
Err 2 NRC 5    <- ошибки ISO-TP и ответы 0x7F
ID 23 FPS512   <- уникальных ID за 30 с и кадров/сек
0x7E8 62F190   <- последнее расшифрованное сообщение
```

## Настройка монитора шины

В начале `autoreadercan.yaml` есть подстановки:

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `log_every_frame` | `"false"` | `true` — печатать **каждый** кадр (на 500 кбит/с это тысячи строк в секунду) |
| `log_throttle_ms` | `"1000"` | не чаще одного лога на ID за этот интервал (мс) |
| `table_dump_ms` | `"10000"` | период сводной таблицы ID, `0` — не печатать |

Чтобы просто смотреть «кто есть на шине», ничего менять не нужно: раз в 10 секунд
в лог приходит таблица всех ID с периодами и последними байтами.

Если действительно нужен полный поток кадров:

```yaml
substitutions:
  log_every_frame: "true"
```

Учтите, что при 500 кбит/с это может быть 2000–4000 строк в секунду — лог
успевает обрабатываться по USB Serial/JTAG, но читать его неудобно. Обычно
достаточно `log_throttle_ms: "500"` вместо полного потока.

Если живой поток кадров не нужен, а нужны только таблица ID и расшифрованный
UDS, поставьте в блоке `logger` уровень `INFO` — строки отдельных кадров
(они пишутся на уровне `DEBUG`) исчезнут, таблица и UDS останутся.

## Какие ID расшифровываются как UDS

Монитор видит все кадры, а в UDS-декодер автоматически отдаются только
диагностические ID:

- `0x7E0..0x7E7` — запросы тестера (11-бит);
- `0x7E8..0x7EF` — ответы ЭБУ (11-бит);
- `0x7DF`, `0x18DB33F1` — функциональные запросы;
- `0x18DAxxxx` — 29-битная диагностика (`0x18DA<target><tester>`).

Если на вашей модели Geely диагностика идёт по нестандартным ID, поправьте
функцию `is_uds_id()` в `uds_decode.h` (она в конце файла, перед монитором).

Если таблица всех ID не нужна и хочется вернуть «тихий» режим, в блоке
`canbus.on_frame` есть закомментированный вариант только с диагностическими
триггерами (`0x7E0`/`0x7E8`/`0x7DF`).

## Важно

- В режиме `LISTENONLY` ESP32 **не отправляет ACK** и вообще ничего не пишет в
  шину, поэтому устройство безопасно оставлять подключённым.
- Пассивный сниффер покажет UDS-трафик только тогда, когда его кто-то генерирует:
  подключённый диагностический сканер, приложение через ELM327 или внутренняя
  диагностика шлюза. Обычные кадры блоков (таблица ID) видны всегда, пока на шине
  есть обмен — достаточно включить зажигание.
- Скорость 500 кбит/с — стандарт для HS-CAN большинства Geely. Если кадров нет
  вообще, проверьте скорость и правильность подключения CAN-H/CAN-L.
- GPIO5/GPIO6 на C3 Mini — обычные выводы, конфликтов с USB (GPIO18/19) нет.
